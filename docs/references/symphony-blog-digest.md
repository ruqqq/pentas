# Symphony — Blog Digest

Source: [An open-source spec for Codex orchestration: Symphony](https://openai.com/index/open-source-codex-orchestration-symphony/) (OpenAI, April 27, 2026)

Authors: Alex Kotliarskyi, Victor Zhu, Zach Brock

This is a digest of the announcement post that accompanied the Symphony [SPEC.md](./symphony-spec.md). It captures motivation, design rationale, and lessons learned — context that does not appear in the spec itself.

## Why Symphony exists

The team had been operating under the constraint that every line in their internal repo had to be generated by Codex (the "harness engineering" experiment). That worked, but exposed a new bottleneck: **human attention**. An engineer could comfortably steward 3–5 interactive Codex sessions before context-switching costs collapsed productivity.

Their reframe: stop optimizing for sessions and PRs and instead optimize for _deliverables_ — tickets, issues, milestones. Let agents pull work from the issue tracker rather than having humans dispatch it.

> "For every open task, guarantee that an agent is running in its own workspace."

That single invariant is the core of Symphony.

## What Symphony is (and isn't)

- A long-running daemon that watches an issue tracker (Linear in v1) and ensures every active issue has a per-issue workspace with a coding agent running in it.
- A scheduler / runner / tracker reader. **Not** a tracker writer — ticket mutations (state changes, comments, PR links) are performed by the coding agent itself using its own tooling.
- Workflow policy lives in-repo as `WORKFLOW.md` (YAML front matter + Liquid prompt body), versioned with the codebase.
- Reference implementation is in Elixir (chosen for its concurrency primitives). The spec is intentionally language-agnostic — Codex one-shot reimplementations in TS, Go, Rust, Java, and Python were used to surface ambiguities.

## Reported impact

- ~500% increase in landed PRs on some teams in the first three weeks.
- Cognitive cost of speculative work drops to near-zero — file a ticket, throw away the result if it's wrong.
- Non-engineers (PMs, designers) can file feature requests directly into the tracker and get a review packet with a video walkthrough.
- Agents can themselves create new tickets when they notice out-of-scope work (perf issue, refactor opportunity), so the backlog becomes self-organizing.

## Design lessons

- **Tickets are larger than PRs.** One issue can fan out into multiple PRs across repos, or be pure investigation that produces no code. Decoupling work from sessions/PRs was central.
- **DAG-style planning emerges naturally.** A ticket can ask the agent to produce an implementation plan; the agent then files a tree of child tickets with `blocked_by` relations. Agents only pick up unblocked tickets, so parallelism falls out automatically.
- **Don't pin agents into rigid state-machine roles.** Early versions only asked Codex to _implement_ a task. That under-used the model. They moved to giving agents _objectives_ (manager-style) and a richer toolbox (`gh` CLI, CI-log skills, etc.) so agents can also close stale PRs, pull reports, address review comments across multiple PRs, etc.
- **The harness, not the orchestrator, is where investment pays off.** When agents miss the mark, the fix is usually a new skill, doc, or guardrail in the harness — not a patch to the orchestrator.
- **Last-mile shepherding matters in big monorepos.** Symphony watches CI, rebases, resolves conflicts, retries flakes — by the time a ticket reaches `Merging`, human babysitting is rarely needed.
- **Symphony does not fit every task.** Ambiguous, judgment-heavy work still belongs in interactive Codex sessions. Symphony is for the bulk of routine implementation, freeing humans for the hard problems.

## Implementation notes worth remembering

- Codex App Server (headless JSON-RPC mode) was the unlock that made programmatic orchestration clean — replaced earlier `tmux`-driven prototypes.
- Linear access tokens are kept out of subagent containers via Codex's _dynamic tool calls_: Symphony advertises a `linear_graphql` tool to the session, which proxies GraphQL calls using the orchestrator's auth. No MCP server, no token leak.
- Symphony was bootstrapped on itself: once a minimal version worked, further Symphony development was done by Symphony.

## How this maps to dalang

dalang is our Claude-Code-driven analogue of Symphony. The narrative above informs several dalang design choices documented in `docs/superpowers/specs/2026-04-29-dalang-orchestrator-design.md`:

- Single in-process daemon, in-memory state, no persistent DB — mirrors Symphony's "tracker-driven recovery" stance.
- `WORKFLOW.md` as the in-repo policy contract, hot-reloaded.
- Per-issue git-worktree workspaces under a shared bare clone (Symphony leaves workspace population to hooks; we standardize on worktrees).
- Papan plays the Linear role — issue tracker as control plane.
- Token accounting is additive sum of per-turn `result.usage` (Claude Agent SDK doesn't expose thread-cumulative counters, unlike Codex's `total_token_usage`).
- Tracker writes belong to the agent, not the orchestrator. Same boundary.

The key philosophical takeaway worth re-reading before any large dalang change: **give the agent objectives and tools, not rigid state transitions.**
