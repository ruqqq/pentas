# CLI Help Implementation Plan

**Issue:** `ruqqq/pentas#5` — Add `--help` command to both binaries

**Goal:** Add a deterministic help path for both installed binaries, `dalang` and `papan`, so users can discover supported flags without starting either server.

**Source context:**

- `CLAUDE.md` repo rules: Bun workspace tooling, TDD, specs/plans as behavior source.
- `docs/superpowers/specs/2026-04-29-dalang-orchestrator-design.md`: `dalang` is the orchestrator daemon; CLI `--port` overrides server config and positional workflow path defaults to `./WORKFLOW.md`.
- `docs/superpowers/specs/2026-04-29-papan-tracker-design.md`: `papan` is the local tracker; SQLite path defaults to `~/.papan/papan.db`, with `PAPAN_DB_PATH` and `PAPAN_PORT` environment overrides.
- Current code:
  - `packages/dalang/src/cli/args.ts` parses workflow path and `--port`.
  - `packages/dalang/src/index.ts` starts `Bootstrap` immediately after parsing.
  - `packages/papan/src/index.ts` parses `--port` and `--db` inline, then starts `runPapan`.

## Acceptance Criteria

- `dalang --help` and `dalang -h` print usage text to stdout and exit successfully without loading `WORKFLOW.md`, probing auth, starting the orchestrator, or binding an HTTP port.
- `papan --help` and `papan -h` print usage text to stdout and exit successfully without opening SQLite, running migrations, or binding an HTTP port.
- Help wins as soon as `--help` or `-h` appears in argv, even if other argv entries would normally be invalid. This keeps help usable as a discovery path and guarantees the runtime short-circuit happens before normal validation/startup.
- Help text documents the existing supported flags and defaults:
  - `dalang [WORKFLOW.md] [--port <port>]`
  - `papan [--port <port>] [--db <path>]`
- Unknown flags remain errors for `dalang`. Papan should stop silently ignoring unknown flags; it should reject them with a clear error so help output is trustworthy.
- Invalid or missing flag values should be covered consistently enough for both CLIs to avoid starting with accidental `NaN`/missing values.
- Tests cover both parser behavior and the "does not start server on help" entry-point behavior where feasible.

## Non-Goals

- No new CLI framework dependency.
- No subcommands beyond help.
- No changes to daemon/tracker runtime behavior after normal argument parsing succeeds.
- No changes to environment variable names or server defaults.

## ADR Decision

No ADR is needed. This is a local CLI surface change, not a durable architecture choice or cross-package contract. The existing package entry points can own small parser/help helpers without changing shared control-plane or runtime boundaries.

## Implementation Steps

### Task 1: Extend dalang argument parsing

Files:

- `packages/dalang/src/cli/args.ts`
- `packages/dalang/tests/cli/args.test.ts`

Steps:

- Add a `help: boolean` field to `ParsedArgs`.
- Treat `--help` and `-h` as help requests. Once seen, return a help parse result before validating any remaining argv entries and without requiring a workflow path.
- Export a `DALANG_HELP` string or `formatDalangHelp()` helper from the parser module.
- Update existing tests for the new `help: false` field.
- Add tests for `--help`, `-h`, and help combined with invalid/unknown args to lock in help-wins precedence.

### Task 2: Wire dalang entry-point early exit

Files:

- `packages/dalang/src/index.ts`
- `packages/dalang/tests/cli/bootstrap.test.ts` or a new `packages/dalang/tests/cli/index.test.ts`

Steps:

- After `parseArgs(Bun.argv.slice(2))`, if `help` is true, print help to stdout and `process.exit(0)` before constructing `Bootstrap`.
- Keep the existing startup and shutdown behavior unchanged for normal args.
- Prefer a small exported `main(argv, io)` helper if direct entry-point tests need an injectable stdout/exit surface.

### Task 3: Extract papan argument parsing

Files:

- Create `packages/papan/src/cli/args.ts`
- Create `packages/papan/tests/cli/args.test.ts`
- Update `packages/papan/src/index.ts`

Steps:

- Move inline parsing from `packages/papan/src/index.ts` into a parser that returns `{ port?: number; dbPath?: string; help: boolean }`.
- Add `PAPAN_HELP` or `formatPapanHelp()` documenting `--port`, `--db`, `--help`, and `-h`.
- Treat `--help` and `-h` as help requests. Once seen, return a help parse result before validating any remaining argv entries.
- Validate `--port` like dalang: value required, integer, and `>= 0`.
- Validate `--db`: value required and non-empty.
- Reject unknown flags and unexpected positional args.
- Keep environment fallback behavior in `runPapan()` unchanged.

### Task 4: Wire papan entry-point early exit

Files:

- `packages/papan/src/index.ts`
- Optional new `packages/papan/tests/cli/index.test.ts`

Steps:

- If the parsed args request help, print help and exit before calling `runPapan`.
- Normal startup should still call `runPapan({ port, dbPath })`.
- Add an entry-point-level test if the helper extraction makes it low-friction; otherwise parser tests plus manual command verification are acceptable for this narrow surface.

### Task 5: Verify

Run from repo root:

- `bun test packages/dalang/tests/cli packages/papan/tests/cli`
- `bun test`
- `bun run typecheck`
- `bun run lint`

Manual checks:

- `bun run packages/dalang/src/index.ts --help`
- `bun run packages/papan/src/index.ts --help`

Expected manual result: usage text printed and commands return `0` without server startup logs.

## Risks

- Directly testing executable entry points can accidentally start long-lived servers; prefer extracted `main()` helpers or parser-level tests to keep tests deterministic.
- Papan currently accepts invalid args loosely. Tightening unknown/invalid flag handling is user-visible, but it aligns with the help feature and avoids misleading documentation.
